## 1. Grok consumer and business apps: connectors, custom remote MCP, scheduled tasks, projects, memory, custom assistants, business plans, presence in X and messaging apps. What can run unattended?

### Takeaway
"Grok" is now three separate products with different connectivity: the **Grok app** (grok.com, iOS, Android) has connectors including bring-your-own remote MCP (since 2026-05-06) and **Automations** that run on a schedule or on an incoming email (since 2026-07-16); **Grok Bot** (beta since 2026-08-11) is an always-on agent on a cloud computer with **routines** triggered by schedule, email, webhook, Slack and other events; **Grok Build** is the coding agent. Both the app and Grok Bot can work unattended, but only Grok Bot can be started by another system (a webhook), and Grok Bot is tied to a Cursor account and a paid plan.

### Inferences
- What can run unattended, in order of effort: (1) a Grok app Automation on a schedule, for everyone; (2) a Grok app Automation fired by an incoming email, with SuperGrok; (3) a Grok Bot routine fired by schedule, email, webhook or Slack/GitHub/Linear events, on plans that include Grok Bot. Only (3) can be started directly by another system.
- For a non-programmer, the lowest-effort way to plug Grok into a shared hub is: add the hub as a custom MCP connector at grok.com/connectors, then create an Automation that @-mentions it. This is a "pull" model: Grok wakes on a timer, reads its tasks, writes results back.
- Choosing Grok Bot means also taking on a Cursor account, separate usage metering, and a product still in beta. That is a bigger commitment than "one more chat app".
- Custom assistants in the sense of a custom GPT do not appear in the official material I read for the Grok app; the nearest equivalents are Skills (reusable instructions) and Grok Bot's Bots with a job, Team Bots and Bot templates.

### Gaps
- Whether a Grok app Automation can call a **custom** MCP connector on every run is not stated explicitly; the announcement only says automations can use connectors via @.
- Whether custom MCP connectors are free-tier or paid: official docs and third-party guides disagree.
- No official page found for Projects, Workspaces or Memory in the current Grok docs; the sources are from 2025.
- A search snippet mentioned a "Custom Agents" feature launched 2026-03-04 (up to four agents with their own instructions); I could not open a source for it before the search budget ran out. Treat as unverified.
- Current Grok Business and Enterprise prices under the X Subscription are not confirmed beyond the team-seat list prices; the $30 per user figure is from December 2025.
- Limits on number of connectors, tools per connector, and Automations per account are not published.
- I could not read x.ai/news as a list (HTTP 403), so smaller launches may be missing.

## 2. xAI developer API: function calling, remote MCP tools, built-in agent tools, agent framework, coding agents, collections, OpenAI compatibility, pricing. What would it take to run a Grok-based agent that reads and writes a shared hub and that other systems can call?

### Takeaway
The xAI API is an OpenAI-style API (`https://api.x.ai/v1`, Responses API recommended) with client-side function calling, server-side tools (web search, X search, code execution, collections search, image generation) and a **remote MCP tool that xAI executes on its side at no per-call fee**, so one HTTPS request can make Grok read and write an MCP hub. There is no hosted agent runtime with its own inbound address, no background mode and no webhooks: to make a Grok agent callable by other systems you host a thin wrapper yourself (or use Grok Bot's webhook, or run Grok inside Microsoft Foundry or Google Cloud).

### Cited Findings

#### Endpoints and compatibility
- "The Responses API is the recommended way to interact with SpaceXSI models"; Chat Completions is labelled legacy/deprecated and supports "Function calling only", while the Responses API has "Native support for tools (search, code execution, MCP)". Responses keep conversation state through `previous_response_id`; "Responses stored for 30 days." — [docs.x.ai Responses vs Chat Completions, undated](https://docs.x.ai/developers/model-capabilities/text/comparison) [F]
- The OpenAI SDK works by setting `base_url` to `https://api.x.ai/v1` with the key in `XAI_API_KEY`; examples also use the xAI SDK (Python) and the Vercel AI SDK. — [docs.x.ai Function calling, undated](https://docs.x.ai/developers/tools/function-calling) [F]
- "The Anthropic SDK compatibility is fully deprecated"; migrate to the Responses API or gRPC API. — [docs.x.ai Legacy and deprecated endpoints, undated](https://docs.x.ai/developers/rest-api-reference/inference/legacy) [F]
- Responses endpoints: `POST /v1/responses`, `GET /v1/responses/{response_id}`, `DELETE /v1/responses/{response_id}`; bearer-token auth. A `background` parameter exists but is marked "(Unsupported)"; no webhooks or callbacks are documented. `max_turns` caps agentic tool-calling turns. — [docs.x.ai Responses API reference, undated](https://docs.x.ai/developers/rest-api-reference/inference/responses) [F]
- The docs publish a machine-readable OpenAPI specification (docs.x.ai/openapi.json) and a docs MCP server. The index has no page for an agent SDK or framework, webhooks, or A2A. — [docs.x.ai/llms.txt, read 2026-11-23](https://docs.x.ai/llms.txt) [F]

#### Function calling (client-side tools)
- "The model requests the call, you execute it locally, and return the result." Tools are defined with a name, description and JSON Schema parameters; `tool_choice` can be auto, required, none or a named function; parallel calls are on by default; up to 350 tools per request. Built-in tools and custom function tools can be combined in one request. — [docs.x.ai Function calling, undated](https://docs.x.ai/developers/tools/function-calling) [F]
- The tool limit is stated differently elsewhere: the Responses reference says up to 1,000 tools; InfoQ reported "up to 128 tools per request" in May 2026. — [docs.x.ai Responses API reference](https://docs.x.ai/developers/rest-api-reference/inference/responses) [F]; [InfoQ, 2026-05-22](https://www.infoq.com/news/2026/05/xai-grok-skills/) [F]

#### Remote MCP tools (server-side)
- Remote MCP tools are supported in three places: the xAI native SDK, the OpenAI-compatible Responses API and the Speech to Speech (voice) API. "SpaceXSI manages the MCP server connection and interaction on your behalf." — [docs.x.ai Remote MCP tools, undated](https://docs.x.ai/developers/tools/remote-mcp) [F]

### Inferences
- Minimum build for "a Grok agent that reads and writes a shared hub": (a) the hub exposes a remote MCP server over HTTPS with a bearer token; (b) a caller sends `POST https://api.x.ai/v1/responses` with the model, instructions and one `mcp` tool pointing at the hub; (c) xAI's servers call the hub's tools and return the final answer. No Grok-side hosting is needed, and the same request shape is close to OpenAI's Responses API.
- To be "callable by other systems", someone must own a small always-on service (or a scheduled job) that receives the task and makes that API call, because xAI offers no hosted agent endpoint, no background mode and no webhooks. Synchronous calls, the Batch API or deferred completions (polling) are the only return paths.
- Because `require_approval` is not supported, a human-approval step for write actions has to live in the hub (for example, the hub parks risky writes as "pending") or the agent must be limited to read tools with `allowed_tools`.
- If the hub only has a plain HTTP API, the same agent can be built with client-side function calling, but then the wrapper service must execute each call itself; the MCP route removes that work.
- Cost of the MCP route is model tokens only; with all tool definitions injected into context, a small, well-named tool list on the hub keeps cost and errors down.
- For an organization already on Microsoft 365, running Grok as a model inside Microsoft Foundry is an alternative that keeps billing and identity in Azure, at the price of possible feature gaps versus api.x.ai.

## 3. Inbound and outbound in practice for Grok: how can it receive a task from another agent or an orchestrator and return a result; what is impossible today?

### Takeaway
Outbound is easy on every Grok surface (connectors, custom MCP, function calling). Inbound has exactly three doors today: a **Grok Bot routine webhook**, a **direct call to the xAI API** (you bring the wrapper), and **indirect triggers** (a schedule, an email, a Slack message or an @bot tag on X). There is no documented API or webhook into the consumer Grok app, no callback when work finishes, and no agent-to-agent endpoint.

### Cited Findings
- Grok app Automations start only from a schedule, a matching incoming email (SuperGrok) or a manual "Run now"; webhook and API triggers are not mentioned. Results come back as a saved conversation plus optional email or app notification. — [x.ai news, 2026-07-16](https://x.ai/news/grok-automations) [F]
- Grok Bot routines accept "an HTTP POST to a routine-specific URL with a Bearer key and an optional JSON body"; a 200 means the run started, not that it finished. Results appear in the Bot's chat, and routines can post linked outputs to a conversation. An API trigger other than the webhook is not mentioned. — [docs.x.ai Grok Bot skills and routines, undated](https://docs.x.ai/grok-bot/skills-routines-and-automations) [F]
- Grok Bot can also be triggered by email to the Bot's address, Slack mentions and messages, and events from GitHub, Linear, Sentry and PagerDuty. — [docs.x.ai Grok Bot skills and routines, undated](https://docs.x.ai/grok-bot/skills-routines-and-automations) [F]
- Bot-to-Bot hand-offs exist only between Grok Bots; the documentation does not describe external agents as participants, and does not mention A2A, an MCP server exposed by a Bot, or an API for talking to a Bot from outside. — [docs.x.ai Grok Bot chat and collaboration, undated](https://docs.x.ai/grok-bot/chat-and-collaboration) [F]
- Deep links can open a Bot with a prefilled message but do not send it. — [docs.x.ai Grok Bot deep links, undated](https://docs.x.ai/grok-bot/deep-links) [F]
- xAI API: a caller holding an API key can post a task to `/v1/responses` and receive the result in the response; state can be continued for 30 days with `previous_response_id`; `background` is unsupported and no webhooks exist. — [docs.x.ai Responses API reference, undated](https://docs.x.ai/developers/rest-api-reference/inference/responses) [F]
- Outbound from the app: custom MCP connectors must be reachable from the public internet; private addresses are rejected. — [docs.x.ai Custom MCP tunneling, undated](https://docs.x.ai/grok/connectors/custom-mcp-tunneling) [F]
- Outbound from the API: remote MCP calls are made by xAI's servers with an optional Authorization token and extra headers. — [docs.x.ai Remote MCP tools, undated](https://docs.x.ai/developers/tools/remote-mcp) [F]
- Outbound from Grok Bot: connected apps, custom MCP servers, plugins built around an API, and the browser on its cloud computer for sites with no API. Enterprise teams can set a network policy and inference hooks. — [docs.x.ai How Grok Bot works, undated](https://docs.x.ai/grok-bot/how-grok-bot-works) [F]

### Inferences
- Three workable patterns for "Grok as one more agent" on a shared hub:
  1. **Pull, no code (Grok app):** hub as custom MCP connector plus a scheduled Automation that reads "tasks for Grok" and writes results back. Latency equals the schedule; the hub is both inbox and outbox.
  2. **Push, low code (Grok Bot):** the orchestrator calls the routine webhook with a JSON body (for example a task id); the Bot does the work and writes the result back to the hub through MCP. Because the webhook only acknowledges the start, the result must travel through the hub, not through the HTTP response.
  3. **Push, own code (xAI API):** a small service receives the task, calls the Responses API with the hub as an MCP tool, and returns or stores the result. This is the only pattern that gives a synchronous answer.
- Email is a universal fallback inbound door: both the Grok app (SuperGrok) and Grok Bot can start work from an incoming email, so an orchestrator that can send email can reach Grok without any API.
- Impossible or undocumented today: pushing a task into a consumer Grok chat by API; getting a completion callback from Grok Bot or the xAI API; registering Grok as an A2A agent in another vendor's console; having a non-Grok agent join a Grok Bot group chat; reaching a hub on a private network from the Grok app without a tunnel; requiring per-call approval for MCP tools in the xAI API.

### Gaps
- Not confirmed whether a Grok Bot webhook run can return a result URL or run id that can be polled.
- Not confirmed whether Team Bots accept webhook triggers; the Team Bots page describes only chat, Slack, Teams and meetings.
- I found no statement on whether Grok app Automations expose run history through any API.

## 7. Across all vendors studied: the common denominator a vendor-neutral hub should target, and what still differs per vendor

### Takeaway
The common denominator is a **remote MCP server on a public HTTPS address, using the Streamable HTTP transport, exposing a small set of tools, with OAuth (including Dynamic Client Registration) and a static bearer-token option**, backed by a **plain HTTPS/JSON API described by OpenAPI** for function calling and for agents that prefer raw APIs. A2A is native only on Google's side (and on Microsoft and AWS agent platforms), so it is an optional adapter, not the baseline. What differs per vendor is not the protocol but the gates around it: plan, admin approval, account type and region, approval prompts, and above all how a task gets in and how a result gets out.

### Inferences
- **What the hub should offer so a new assistant plugs in with the least work:**
  1. One remote MCP server, public HTTPS, Streamable HTTP transport (SSE is being dropped by some clients and is awkward behind tunnels).
  2. Everything exposed as **tools**, few in number, clearly named, with read tools separated from write tools so each vendor's filter or approval rule can be applied (`allowed_tools` in xAI, per-function permissions in Mistral, write confirmation in Gemini).
  3. Two ways to authenticate to the same server: OAuth 2.1 with Dynamic Client Registration for consumer apps that expect a sign-in flow (Gemini, Mistral, Grok), and a static bearer token per agent for APIs and scripts (xAI API, Perplexity Agent API, Grok Build, Manus).
  4. The same operations as a plain HTTPS/JSON API with an OpenAPI description, for function calling in any vendor's API and for agents that call APIs directly (Manus, Grok Bot plugins, DeepSeek-based agents).
  5. A task inbox and outbox inside the hub ("what is assigned to me", "here is my result"), because that is the only hand-off that works with every assistant: those with no inbound door simply poll on a schedule.
  6. Risky writes held for human approval inside the hub, since approval behaviour at the assistant side ranges from "always asks" to "cannot ask".
- **With that in place, adding an assistant is a short checklist, not a project:** (a) does it accept a custom MCP URL on the plan and account type in use; (b) who must approve it (user, workspace admin, cloud admin); (c) how does it wake up (schedule, email, webhook, API, event); (d) where does its result go (always back to the hub); (e) what can it write without asking.
- **For "tomorrow I might want to use Grok" specifically:** a hub that already serves a remote MCP server to Claude and a plain HTTP API to a custom GPT needs no new protocol for Grok. The Grok app takes the MCP URL directly and an Automation gives it a heartbeat; Grok Bot adds a webhook if push is needed; the xAI API takes the same MCP URL in one request.
- **What will keep differing per vendor and should be expected, not engineered away:** plan and price gates; admin provisioning; regional and account-type limits (Gemini custom apps, Grok @bot tagging, Meta Muse); authentication flavour; approval prompts; trigger types and minimum intervals (5 minutes for Grok Bot routines, 15 minutes for Perplexity); whether a completion callback exists (Manus yes, Grok Bot and xAI no); and product churn (Le Chat became Vibe, Gems are becoming Skills, Gemini CLI is giving way to Antigravity CLI, xAI was renamed twice in 2026).
- **A2A is worth an adapter only when a target platform demands it** (Gemini Enterprise's gallery, and by the foundation's account Microsoft's and AWS's agent platforms). It would not help with Grok, Perplexity, Mistral, Meta, DeepSeek or Manus today.
- A method built on "the hub holds the tasks and results, every assistant reaches it through MCP or plain HTTP" survives the addition of any assistant in this study except the two closed ones (Meta's consumer agent and DeepSeek's app), and those can still be reached by a person pasting, or by email where supported.

### Gaps
- ChatGPT, Microsoft 365 Copilot and Claude were out of my scope; their rows are not in the table and must come from the other researchers' notes before a full common-denominator claim is made.
- I did not test any connection; every statement is from documentation or press, and several vendor pages are undated.
- Whether each consumer assistant's scheduled feature can call a custom MCP server on every run is confirmed only for Perplexity (connectors linked to Computer) and is unstated for Grok Automations, Gemini Tasks and Mistral scheduled tasks.
- MCP specification versions and optional features (for example the Tasks extension that Perplexity's server uses) differ by client; I did not map which protocol revision each assistant implements.
