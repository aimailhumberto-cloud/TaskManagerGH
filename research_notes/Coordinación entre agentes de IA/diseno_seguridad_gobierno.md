## 1. Coordination designs and when each fits (ownership, acknowledgements, retries, idempotency, conflicting writes, single source of truth, task lifecycle, approval gates)

### Takeaway
Every major vendor catalogue now says the same thing: start with one agent, add a second only for a named reason, and prefer a central coordinator with one writer over free peer-to-peer chatter. For a personal hub, the pattern best supported by evidence is "hub as single source of truth plus a task list with explicit states, short-lived claims, idempotent submissions and human approval on write actions", using the state names the A2A 1.0 protocol already standardised.

### Cited Findings

#### Pattern catalogues
- [GUIDANCE] Microsoft's Azure Architecture Center lists three levels of complexity (direct model call, single agent with tools, multi-agent orchestration) and says "Use the lowest level of complexity that reliably meets your requirements"; a single agent with tools is "Often the right default for enterprise use cases". Article dated 2026-02-12, page updated 2026-09-21 *(opened)* — [Azure Architecture Center, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [GUIDANCE] The same guide names five multi-agent patterns and their weak points: sequential (pipeline; "Failures in early stages propagate"), concurrent (fan-out/fan-in; "Requires conflict resolution when results contradict"), group chat (shared thread with a chat manager; "Conversation loops"), handoff (one active agent at a time; "Infinite handoff loops. Unpredictable routing paths") and magentic (a manager builds and updates a task ledger; "Slow to converge. Stalls on ambiguous goals"). Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [GUIDANCE] OpenAI's Agents SDK documentation distinguishes orchestration decided by the model from orchestration decided by code (code makes speed, cost and behaviour more predictable) and two multi-agent shapes: "agents as tools", where a manager keeps control and owns the final answer, and "handoffs", where a triage agent passes the conversation to a specialist that then answers directly. Living documentation, undated *(opened)* — [OpenAI Agents SDK, Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)
- [GUIDANCE] Confluent describes four event-driven multi-agent patterns that match the classic list: orchestrator-worker, hierarchical, blackboard and market-based. Published 2025-02-19 (first on InfoWorld 2025-01-28). The authors work for a vendor of event-bus software and give no measurements *(opened)* — [Confluent, A Distributed State of Mind: Event-Driven Multi-Agent Systems](https://www.confluent.io/blog/event-driven-multi-agent-systems/)

#### Orchestrator with workers / supervisor
- [GUIDANCE] Anthropic's production research system uses an orchestrator-worker design: a lead agent plans, spawns 3–5 subagents in parallel with their own context windows, and synthesises their results; each subagent needs an objective, an output format, guidance on tools and sources, and clear task boundaries. Published 2025-06-13 *(opened)* — [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- [MEASURED] In Google Research's controlled comparison, agents working independently amplified errors "by up to 17.2x", while a centralized (hub-and-spoke) orchestrator contained amplification to 4.4x; the authors describe the orchestrator as a "validation bottleneck". Blog dated 2026-01-28 *(opened)* — [Google Research blog, Towards a science of scaling agent systems](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)
- [OPINION, with product metrics] Cognition (maker of the Devin coding agent) reports that a manager agent that splits a task, spawns child agents and coordinates them through an internal MCP server is "live in Devin today", and recommends a "map-reduce-and-manage" structure over unstructured swarms, which it calls "mostly a distraction". Published 2026-04-22 *(opened)* — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- [MEASURED, engineering report] Cursor tried three coordination designs with hundreds of concurrent coding agents. Planners that create tasks, workers that only execute them and a judge that decides whether to continue solved most of the coordination problems; removing a separate integrator role helped because it had created more bottlenecks than it solved. Published 2026-01-14 *(opened)* — [Cursor, Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents)

#### Hand-offs between peers
- [GUIDANCE] In the handoff pattern "Full control transfers from one agent to another agent" and "Only one agent at a time operates on the original input"; Microsoft says to avoid it when routing is deterministic or when bouncing between agents is hard to prevent. Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [GUIDANCE] Anthropic warns that splitting work by role (planner, implementer, tester, reviewer) creates a "telephone game" with lossy hand-offs; in one role-based experiment subagents "spent more tokens on coordination than on actual work". Its rule: "Decomposition follows context, not problem type." Published 2026-01-23 *(opened)* — [Anthropic, Building multi-agent systems: when and how to use them](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- [MEASURED] In the MAST failure study, about 32% of annotated failures fall under inter-agent misalignment (for example reasoning–action mismatch 13.2%, task derailment 7.4%, failing to ask for clarification 6.8%). arXiv v3 dated 2025-10-26; category share computed from the per-mode percentages in v3 *(opened)* — [Cemri et al., Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/html/2503.13657v3)

#### Blackboard / shared state
- [GUIDANCE] Microsoft lists "Sharing mutable state between concurrent agents, which can result in transactionally inconsistent data" among common pitfalls, and recommends persisting shared state in an external durable store while scoping it "to the minimum necessary information". Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [GUIDANCE] In group-chat orchestration all agents and humans write into one accumulating thread, which "provides transparency and auditability"; agents are typically read-only, and Microsoft suggests "limiting group chat orchestration to three or fewer agents". Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [MEASURED, abstract only] A 2025 paper adds a blackboard to LLM multi-agent systems (all agents see all shared information; the next agent is chosen from the blackboard's content) and reports the best average performance against static and dynamic multi-agent baselines with fewer tokens; the abstract gives no figures. Submitted 2025-07-02 *(opened, abstract)* — [Han and Zhang, Exploring Advanced LLM Multi-Agent Systems Based on Blackboard Architecture](https://arxiv.org/abs/2507.01701)
- [SPEC] OWASP's MCP Top 10 (beta) lists "MCP10:2025 – Context Injection & Over-Sharing": shared or persistent context exposes one task's sensitive data to another. Beta, no publication date shown *(opened)* — [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/)

#### Publish/subscribe event bus
- [GUIDANCE] In the event-driven versions, the orchestrator writes commands to a topic, workers form a consumer group, events with the same key go to the same partition to keep order, a failed worker's work "can be replayed from a given partition for a saved offset", and the immutable log acts as the single source of truth. Published 2025-02-19; vendor architecture, no retry policy described *(opened)* — [Confluent](https://www.confluent.io/blog/event-driven-multi-agent-systems/)
- [SPEC] A2A 1.0 offers streaming and push notifications as optional capabilities: notifications are HTTP POSTs to a client-provided webhook, and a task stream "MUST close when the task reaches a terminal state". Version 1.0.0, fetched 2026-11-23 *(opened, first 100,000 characters)* — [A2A Protocol Specification](https://a2a-protocol.org/latest/specification/)

#### Task queue with claims or leases
- [SPEC] Amazon SQS shows the standard lease mechanism: a received message becomes invisible to other consumers for a visibility timeout (default 30 seconds, maximum 12 hours); "If you don't delete it before the timeout expires, the message becomes visible again in the queue and can be retrieved by another consumer". Delivery is at-least-once, so duplicates are possible; long work extends the lease with a heartbeat; repeated failures go to a dead-letter queue. Living documentation *(opened)* — [AWS, Amazon SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)
- [GUIDANCE] AWS's idempotency guidance: "An idempotent operation is one where a request can be retransmitted or retried with no additional side effects." The caller sends a unique request identifier; a duplicate gets a semantically equivalent response instead of creating a second resource; the same identifier with different parameters is rejected as a mismatch. Undated Builders' Library article by a principal engineer *(opened)* — [AWS Builders' Library, Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)
- [MEASURED, engineering report] Cursor's first design, flat peers with a shared file and locks, failed: "Agents would hold locks for too long, or forget to release them entirely", and "Twenty agents would slow down to the effective throughput of two or three". Optimistic concurrency (reads free, writes fail if state changed) was more robust, but without hierarchy "No agent took responsibility for hard problems or end-to-end implementation". Published 2026-01-14 *(opened)* — [Cursor](https://cursor.com/blog/scaling-agents)
- [MEASURED, engineering report] An Anthropic researcher ran 16 parallel agents with no orchestrator: each agent claims a task by writing a lock file to a `current_tasks/` folder and git synchronisation forces a second claimant to pick something else. It worked for independent tasks but broke when the work was one big task: "Every agent would hit the same bug, fix that bug, and then overwrite each other's changes." Published 2026-02-05 *(opened)* — [Anthropic, Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler)

#### Marketplace / contract-net
- [SPEC, historical] The Contract Net Protocol (Reid G. Smith, 1980; later standardised by FIPA) has a manager announce a task, contractors bid, the manager award it and the contractor report the result. Known limits: contractors face no penalty for abandoning tasks, and broadcast calls can overload the network. Encyclopedia entry *(opened)* — [Wikipedia, Contract Net Protocol](https://en.wikipedia.org/wiki/Contract_Net_Protocol)
- [MEASURED, simulation] Microsoft Research's Magentic Marketplace (100 customer agents, 300 business agents, synthetic data) found that all models strongly favoured the first proposal received, that welfare fell as agents were shown more options (for example one model fell from about 1,800 to 600), and that some models had all payments redirected to a manipulative agent by prompt injection. Conclusion: "Oversight is critical for high-stakes transactions. Agents should assist, not replace, human decision-making." Published 2025-11-05 *(opened)* — [Microsoft Research, Magentic Marketplace](https://www.microsoft.com/en-us/research/blog/magentic-marketplace-an-open-source-simulation-environment-for-studying-agentic-markets/)
- [INCIDENT] Open discovery between agents has already been abused: on ServiceNow's Now Assist, default agent-discovery settings let a low-privilege agent that read a poisoned record recruit a higher-privilege agent to copy or exfiltrate data ("second-order prompt injection"). Disclosed by AppOmni in November 2025; ServiceNow called it expected behaviour and updated documentation *(secondary; from search summary)* — [The Hacker News](https://thehackernews.com/2025/11/servicenow-ai-agents-can-be-tricked.html); [AppOmni](https://appomni.com/ao-labs/ai-agent-to-agent-discovery-prompt-injection/)

#### Task lifecycle models and protocol status
- [SPEC] A2A 1.0.0 defines these task states: SUBMITTED, WORKING, INPUT_REQUIRED, AUTH_REQUIRED, COMPLETED, FAILED, CANCELED, REJECTED (plus UNSPECIFIED). COMPLETED, FAILED, CANCELED and REJECTED are terminal; INPUT_REQUIRED and AUTH_REQUIRED are "interrupted" states that wait for a person or credential. Fetched 2026-11-23 *(opened)* — [A2A Protocol Specification](https://a2a-protocol.org/latest/specification/)
- [SPEC] Ownership and duplicates in A2A: "Task IDs are server-generated when a new task is created in response to a Message" (the agent that accepts the work owns the task record); a contextId groups related tasks; "Send Message operations MAY be idempotent. Agents may utilize the messageId to detect duplicate messages"; cancel is idempotent; servers "MAY include retry guidance (e.g., Retry-After header in HTTP)". Fetched 2026-11-23 *(opened)* — [A2A Protocol Specification](https://a2a-protocol.org/latest/specification/)
- [SPEC] A2A 1.0 is described by the Linux Foundation as the project's first stable specification, with signed Agent Cards for cryptographic identity, multi-tenancy and multiple protocol bindings; more than 150 organisations support it and it is integrated into Azure AI Foundry, Copilot Studio and Amazon Bedrock AgentCore Runtime. Press release 2026-04-09. Sources disagree on the release day: 2026-03-12 (Turing Post), 2026-03-19 (Linux Foundation post on X), 2026-04-09 (press release) *(opened; date conflict from search summary)* — [Linux Foundation press release](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year); [Turing Post](https://www.turingpost.com/p/a2a); [Linux Foundation on X](https://x.com/linuxfoundation/status/2034664056125030641)
- [SPEC] The same release positions the two protocols as complementary: A2A covers how agents communicate across organisational boundaries, MCP covers how an agent connects to tools and data. 2026-04-09 *(opened)* — [Linux Foundation press release](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)
- [SPEC] The MCP specification of 2026-07-28 made the protocol core stateless (no protocol sessions or initialize handshake), added "multi round-trip requests" in which a server answers `input_required` and the client retries with the answers, moved long-running Tasks into an official extension polled with `tasks/get` and updated with `tasks/update`, and deprecated Dynamic Client Registration, Roots, Sampling, Logging and the HTTP+SSE transport. Published 2026-07-28 *(opened)* — [MCP blog, The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/); [MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- [GUIDANCE] The magentic pattern keeps a "task and progress ledger" that the manager updates as work advances and that gives "a complete audit trail of the evolving plan". Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)

#### Reliability, retries and conflicting writes
- [GUIDANCE] Microsoft's reliability list for agent orchestration: timeouts and retries, graceful degradation, "Surface errors instead of hiding them", "Validate agent output before you pass it to the next agent", circuit breakers, and checkpoints to recover an interrupted run. Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [GUIDANCE] Anthropic: "Agents are stateful and errors compound"; its system resumes from the point of failure with retry logic and regular checkpoints instead of restarting. 2025-06-13 *(opened)* — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- [OPINION] Cognition's two principles: "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results". Published 2025-06-12 *(opened)* — [Cognition, Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)
- [OPINION, with product metrics] Cognition's 2026 update: "multi-agent systems work best today when writes stay single-threaded"; other agents should contribute analysis, not actions. Published 2026-04-22 *(opened)* — [Cognition](https://cognition.com/blog/multi-agents-working)
- [OPINION] LangChain's synthesis of the Anthropic and Cognition posts: "Read actions are inherently more parallelizable than write actions"; conflicting writes cause worse problems than conflicting reads, and Anthropic kept the final report writing with a single agent. Published 2025-06-16 *(opened)* — [LangChain, How and when to build multi-agent systems](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)

#### Human approval gates
- [GUIDANCE] Microsoft: decide which points need human input and whether it is optional or mandatory; "Mandatory gates make the orchestration synchronous at that step, so persist state at these checkpoints", and "scope HITL gates to specific tool invocations rather than full agent outputs so that the orchestration can proceed autonomously for low-risk actions". Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [GUIDANCE] Unit 42 recommends that approval for sensitive actions go through "a separate channel the LLM cannot influence", such as a fixed interface element or a push notification. Published 2025-10-31 *(opened)* — [Palo Alto Networks Unit 42, Agent session smuggling](https://unit42.paloaltonetworks.com/agent-session-smuggling-in-agent2agent-systems/)
- [GUIDANCE] Maker-checker loops need "clear acceptance criteria", an iteration cap, and a fallback such as "escalation to a human reviewer" when the cap is reached. Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)

### Inferences
- Synthesis of how each design answers the six coordination questions (built from the findings above; the wording of the cells is mine):

| Design | Who owns a task | Acknowledgement | Retries and duplicates | Conflicting writes | Single source of truth | Fits when |
| --- | --- | --- | --- | --- | --- | --- |
| Orchestrator with workers (supervisor) | The orchestrator owns the goal and final answer; workers own bounded subtasks | Worker returns a result to the orchestrator | Orchestrator re-issues; needs a request ID to avoid double work | Avoided if only the orchestrator writes | Orchestrator's plan or ledger | Parallel, read-heavy work; one party must answer for the result |
| Hand-offs between peers | Whoever currently holds the conversation; ownership moves | Implicit in the transfer; weak unless logged | Risk of loops and lost context | One active agent at a time, so few conflicts | None by default; must be added | The right specialist only becomes clear mid-task |
| Blackboard / shared state | Nobody by default | None by default | Agents may redo or overwrite | High risk unless one writer or version checks | The board itself | Small groups building on each other's notes; also a channel for poisoned content |
| Publish/subscribe bus | The subscriber group that consumes the event | Offset commit or explicit reply event | Replay from the log; consumers must be idempotent | Order kept per key | The event log | Many independent reactions to the same event; more than one person or team |
| Task queue with claims or leases | The agent holding the current lease | Explicit "done" (delete) before the lease expires | Lease expiry re-queues; at-least-once, so idempotency keys are required | One holder per task; version check on write | The queue or task table | Assistants that only act when asked and poll for work |
| Marketplace / contract-net | The winning bidder | Award and result messages | Re-announce on failure | Per awarded task | The manager's award record | Many interchangeable providers; open ecosystems |

- A hub with an HTTP API and per-person keys maps most naturally onto the task-queue row with an orchestrator's ledger on top: the hub stores every task with A2A-style states, the agent that accepts a task holds a short lease, results are posted with an idempotency key, and anything that changes data waits in an "input required" state for the owner. This is the combination with direct support in the sources (central validation limits error amplification; single-threaded writes; leases and idempotency are the standard cure for duplicates).
- Chat assistants such as a custom GPT or a tenant Copilot normally act only when their user prompts them, so a pull model (the assistant asks the hub what is pending) is more realistic than push events. This is my reading of how these products work and was not verified against vendor documentation in this session.
- Lock-style claims without expiry are a known trap with LLM agents (they forget to release). A lease that expires by itself and an explicit owner field are safer than a "locked" flag.
- The marketplace design brings the most new attack surface for the least benefit at one-person scale: bidding bias, manipulation and discovery abuse are all documented.

## 2. Evidence on effectiveness: when multiple agents help, when they hurt, and what they cost

### Takeaway
Measured results converge: several agents help on wide, parallel, read-mostly work (research, search, independent review) and hurt on sequential or tightly coupled work, and much of the reported gain is simply more tokens spent. Budget for 3–15 times the token use of a single assistant depending on the baseline, and expect the failures to be coordination failures, not model failures.

### Cited Findings

#### Vendor engineering reports
- [MEASURED, internal evaluation] Anthropic's multi-agent research system "outperformed single-agent Claude Opus 4 by 90.2%" on its internal research evaluation; on BrowseComp, token usage alone explained 80% of performance variance and three factors (tokens, tool calls, model choice) explained 95%. Published 2025-06-13; internal evaluation, not independently replicated *(opened)* — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- [MEASURED] Same source on cost: agents use about 4 times the tokens of a chat interaction and multi-agent systems about 15 times; parallel tool calling cut research time by up to 90% for complex queries. 2025-06-13 *(opened)* — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- [GUIDANCE] Same source on fit: good for "valuable tasks that involve heavy parallelization", information that exceeds one context window and many complex tools; a poor fit where all agents need the same context or there are many dependencies between them, and most coding tasks have fewer parallelisable parts than research. Early failure modes included spawning "50 subagents for simple queries" and subagents duplicating each other's work after vague delegation. 2025-06-13 *(opened)* — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- [GUIDANCE] Anthropic's 2026 guidance: "multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks"; they consistently win in three situations (protecting the main context from bulky subtasks, parallel search where the benefit is "thoroughness, not speed", and specialisation when one agent has roughly 20 or more tools); otherwise "the coordination costs typically exceed the benefits". "Start with the simplest approach that works, and add complexity only when evidence supports it." Published 2026-01-23 *(opened)* — [Anthropic](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- [GUIDANCE] Same source on checking work: a verifier agent works well because it needs little context, but it can declare an "early victory" after one or two passing tests, so it needs concrete criteria and negative tests. 2026-01-23 *(opened)* — [Anthropic](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- [MEASURED, product documentation] Claude Code's cost page: "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode"; token use is "roughly proportional to team size"; the feature is off by default behind an experimental setting. Living documentation *(opened)* — [Claude Code docs, Manage costs effectively](https://code.claude.com/docs/en/costs)
- [MEASURED, engineering report] Sixteen parallel Claude agents built a roughly 100,000-line C compiler over nearly 2,000 sessions and two weeks for "just under $20,000" in API costs (2 billion input tokens, 140 million output tokens); the author states it is "not yet a drop-in replacement for a real compiler". Published 2026-02-05 *(opened)* — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)
- [MEASURED, engineering report] Cursor ran hundreds of concurrent agents for weeks (for example a browser of over 1 million lines in about a week) and concluded that "the prompts matter more" than the harness or the model, that different models suit different roles, and that "The best system is often simpler than you'd expect". The large code migration still needed careful human review. Published 2026-01-14 *(opened)* — [Cursor](https://cursor.com/blog/scaling-agents)

#### Practitioner positions
- [OPINION] Cognition, June 2025: default to "a single-threaded linear agent"; splitting a task between subagents that cannot see each other's decisions produces conflicting results (the "Flappy Bird" example); multi-agent collaboration in 2025 produces fragile systems, though "we expect things to change as the field advances". Published 2025-06-12 *(opened)* — [Cognition, Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)
- [OPINION, with product metrics] Cognition, April 2026: a narrower class now works. A review agent with no shared context catches an average of 2 bugs per pull request, about 58% of them severe; a weaker main model consulting a stronger one ("smart friend") works across frontier models; a manager agent delegating to child agents is in production. Parallel-writer swarms still "don't see meaningful adoption", and "The open problems are all communication problems". Published 2026-04-22; figures are the company's own *(opened)* — [Cognition](https://cognition.com/blog/multi-agents-working)
- [OPINION] LangChain: multi-agent systems mainly help by spending more tokens on problems that exceed one agent's limits, are economical only when the task's value justifies the cost, and suit read-heavy work more than interdependent writing. Published 2025-06-16 *(opened)* — [LangChain](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)
- [GUIDANCE] Microsoft: "Decision-making and flow-control overhead often exceed the benefits of breaking the task into multiple agents"; "Multiagent orchestrations multiply model invocations"; magentic runs are the hardest to cost, and each agent should get a model matched to its task. Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)

#### Research papers and benchmarks
- [MEASURED] MAST ("Why Do Multi-Agent LLM Systems Fail?", UC Berkeley and others): 14 failure modes in 3 categories, built from 150 expert-annotated traces (agreement kappa 0.88) and applied to a dataset of more than 1,600 traces from 7 frameworks; the paper reports a "41% to 86.7% failure rate on 7 state-of-the-art (SOTA) open-source MAS". First submitted 2025-03-17, v3 2025-10-26 *(opened)* — [arXiv 2503.13657](https://arxiv.org/abs/2503.13657)
- [MEASURED] MAST shares by category in v3 (my sums of the per-mode figures): system design issues about 44%, inter-agent misalignment about 32%, task verification about 24%. Largest single modes: step repetition 15.7%, reasoning–action mismatch 13.2%, unaware of termination conditions 12.4%, disobeying the task specification 11.8%, incorrect verification 9.1%. v3 dated 2025-10-26 *(opened)* — [arXiv 2503.13657 v3](https://arxiv.org/html/2503.13657v3)
- [MEASURED] MAST interventions on one framework (ChatDev): better role specifications gave +9.4% task success and adding a high-level verification step gave +15.6%; "Current verifier implementations are often insufficient". v3 dated 2025-10-26 *(opened)* — [arXiv 2503.13657 v3](https://arxiv.org/html/2503.13657v3)
- [MEASURED] Google Research, "Towards a Science of Scaling Agent Systems": centralized coordination improved a parallelisable financial-analysis benchmark by 80.9% over a single agent, while every multi-agent variant degraded a sequential planning benchmark by 39–70%; a model using task properties picked the best architecture for 87% of unseen configurations. Blog 2026-01-28 (180 configurations, 4 benchmarks, 3 model families); the arXiv v3 abstract of 2026-04-08 reports 260 configurations and 6 benchmarks with extremes of +80.8% and −70.0% *(opened)* — [Google Research blog](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/); [arXiv 2512.08296](https://arxiv.org/abs/2512.08296)
- [MEASURED] Tran and Kiela: when the reasoning-token budget is held equal, "single-agent systems (SAS) can match or outperform MAS" on multi-hop reasoning (three model families); they also report that API budget controls and benchmark artefacts can inflate apparent multi-agent gains. Submitted 2026-04-02, revised 2026-04-11 *(opened, abstract)* — [arXiv 2604.02460](https://arxiv.org/abs/2604.02460)
- [MEASURED, simulation] OrchBench scores orchestration plans in a deterministic simulator (correlation 0.816 with real executions at about 1.3% of the tokens) and finds that preserving task-critical information matters more than adding agents and that the benefit of parallelism shrinks as coordination failures accumulate. Submitted 2026-07-28 *(opened, abstract)* — [arXiv 2607.25656](https://arxiv.org/abs/2607.25656)
- [MEASURED, simulation] Magentic Marketplace: more options made agents' outcomes worse ("Paradox of Choice") and several models were manipulable by other agents. 2025-11-05 *(opened)* — [Microsoft Research](https://www.microsoft.com/en-us/research/blog/magentic-marketplace-an-open-source-simulation-environment-for-studying-agentic-markets/)

### Inferences
- The three cost multipliers use different baselines and should not be averaged: about 15 times a chat conversation (Anthropic 2025), 3–10 times a single agent on the same task (Anthropic 2026), about 7 times a normal session for a coding agent team (Claude Code documentation).
- The 2026 picture refines the 2025 debate without overturning it: Cognition moved from "don't" to "only with one writer", Anthropic added a cost range and a short list of valid reasons, and independent papers showed that equal-budget comparisons erase much of the advantage on reasoning tasks.
- For a manager with four assistants, the tasks with evidence of benefit are parallel look-ups, cross-checking one assistant's output with another that has not seen the reasoning, and keeping bulky material out of the main conversation. Tasks with evidence of harm are step-by-step work passed from assistant to assistant, and two assistants editing the same thing.
- Four of the five largest MAST failure modes (repetition, not knowing when to stop, ignoring the specification, wrong verification) are things a hub can limit mechanically with step caps, explicit "done" criteria and a required check before a task is closed.

### Gaps
- Anthropic's 90.2% figure is from an internal evaluation; no independent replication was found.
- The Google paper's numbers differ between the January blog and the April arXiv abstract (configurations, benchmarks, fit); both are reported above.
- Tran and Kiela's numerical results were not extracted (abstract only). MAST category shares are my sums from v3; earlier versions and secondary articles quote different splits that I did not verify.
- "Devin Fusion" (announced 2026-06-29; planner model plus cheaper executor, reportedly 46% cost savings) is known only from one secondary outlet and was not checked against Cognition's post — [Crypto Briefing](https://cryptobriefing.com/cognition-devin-fusion-multi-model-coding-agent/)
- A secondary write-up says the 260 configurations average −0.3% against the single-agent baseline; not verified in the paper — [OpenClaw Wiki blog](https://openclawwiki.org/blog/multi-agent-vs-single-agent-what-260-configurations-show)
- No benchmark was found for quality or cost of hand-offs between assistants from different vendors; Cognition's cross-model delegation claim has no numbers.

## 3. Security risks specific to agents that share channels, memory and tools (documented incidents, and what OWASP, NIST and researchers recommend)

### Takeaway
Prompt injection is still unsolved in late 2026 and is now exploited in the wild; every route by which one assistant's text reaches another (messages, shared memory, documents, tool descriptions) is a route for hidden instructions. The recognised defence is architectural: never let the same assistant session combine untrusted content, private data and the ability to send or change things without a human check.

### Cited Findings

#### Core concepts and authority positions
- [OPINION, widely adopted] The "lethal trifecta": "Access to your private data", "Exposure to untrusted content" and "The ability to externally communicate in a way that could be used to steal your data". "LLMs are unable to reliably distinguish the importance of instructions based on where they came from"; MCP "encourages users to mix and match tools from different sources"; guardrail products claiming to catch 95% of attacks are a failing grade in security. Advice: "avoid that lethal trifecta combination entirely". Published 2025-06-16; the post lists Microsoft 365 Copilot, ChatGPT, Claude's iOS app, xAI's Grok and GitHub's MCP server among affected products *(opened)* — [Simon Willison, The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- [GUIDANCE] Meta's "Agents Rule of Two": until prompt injection can be reliably detected, an agent "must satisfy no more than two of the following three properties within a session": "[A] An agent can process untrustworthy inputs", "[B] An agent can have access to sensitive systems or private data", "[C] An agent can change state or communicate externally". If all three are needed, the agent "should not be permitted to operate autonomously" and needs human approval. It is "a supplement — and not a substitute — for common security principles such as least-privilege". ### Inferences
- A shared hub is, in security terms, a shared memory and a message channel at once. Any text an assistant writes into it can carry instructions that another assistant will read later with different permissions; this is exactly the ASI06/ASI07 and "second-order" pattern.
- Authentication does not solve this. In the Unit 42 and ServiceNow cases the sender was a legitimate, authenticated agent that had itself been fed poisoned content. Keys answer "who wrote this", not "is this safe to obey".
- The corporate assistant is the high-value end of any link: it has the private data (property B). If it also reads hub content written by other assistants (property A) and can send or write (property C), the combination the guidance says to avoid is complete.
- Approval prompts shown inside the assistant's own window are weak: two late-2026 cases bypassed or auto-clicked them. Approval should be enforced by the hub itself, on a screen the assistants cannot operate.
- Vendors frequently fix agent flaws without a CVE or advisory, so "no CVE" for a product says little about its exposure.

### Gaps
- I found no documented real-world incident in which an injection travelled between consumer assistants of different vendors through a user-owned hub; the closest are the Rehberger and Unit 42 demonstrations and the single-vendor ServiceNow case.
- The full OWASP agentic Top 10 document (entry details, the "least agency" principle) and OWASP's Q1 2026 incident round-up were not opened; the latter is cited only through CSA.
- NIST has published no final agent-specific security guidance that I could locate; the programme and overlay project were renamed in October–November 2026 and should be re-checked.
- Conflicts not resolved: SearchLeak severity (9.1 versus 6.5–7.5); the Manus agent flaw found by Salt Labs is dated September 2026 by one source and 1 October 2026 by another (secondary only) — [Aviatrix](https://aviatrix.ai/threat-research-center/manus-prompt-injection-vulnerability-2026/).
- Because the search budget ran out, these well-known 2025–2026 cases from my background knowledge were not re-verified and are therefore not listed as findings: ShadowLeak and ZombieAgent (ChatGPT connectors and memory), AgentFlayer (poisoned document via ChatGPT connectors), ForcedLeak (Salesforce Agentforce), CamoLeak (GitHub Copilot Chat), the OpenClaw malicious-skills campaign, and the Anthropic Git MCP server CVEs.
- The MCP exposure percentages come from aggregators without an identified primary report.

## 4. Practical mitigations for a small hub

### Takeaway
Each item on the usual short list (one key per agent, least privilege, read separate from write, allowlists, "content is data", human approval, audit log, rate and cost limits) is backed by a specification rule, an institutional recommendation or a specific incident where its absence caused the damage. None of them needs enterprise tooling; they are design decisions in the hub.

### Cited Findings
- [SPEC] One identity and key per agent, never shared or forwarded: accepting or forwarding tokens issued for something else means the server "will be unable to identify or distinguish between MCP Clients", which the MCP specification forbids outright *(opened)* — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)
- [INCIDENT] What goes wrong without it: a gateway that let a client header override its own credential lost per-user permissions and audit attribution (2026-11-13) *(aggregator, primary not opened)* — [IBM advisory](https://www.ibm.com/support/pages/node/7296490) via [awesome-ai-agent-attacks](https://github.com/webpro255/awesome-ai-agent-attacks)
- [MEASURED] Only 46% of organisations in IBM's 2026 study secured non-human identities, including agent credentials, in AI workflows. Report released 2026-07-29 *(secondary)* — [ComplexDiscovery](https://complexdiscovery.com/policy-without-control-the-ai-governance-gap-in-ibms-2026-cost-of-a-data-breach-report/)
- [GUIDANCE] Least privilege: minimise tools, functions and permissions, and enforce authorisation "in downstream systems rather than relying on an LLM to decide" *(opened)* — [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- [SPEC] Start each key with low-risk read scopes and raise privileges only for the specific operation; avoid wildcard scopes *(opened)* — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)
- [INCIDENT] Separate read from write: in the Supabase case, read-only mode would have removed the channel used to leak the data. 2025-07-06 *(secondary, opened)* — [Simon Willison](https://simonwillison.net/2025/Jul/6/supabase-mcp-lethal-trifecta/)
- [GUIDANCE] After the April 2026 coding-agent leaks, the advice was to remove command-line and write access from review agents, give them read-only access to the repository, and put writes behind human approval. 2026-04-21 *(secondary, opened)* — [VentureBeat](https://venturebeat.com/security/ai-agent-runtime-security-system-card-audit-comment-and-control-2026)
- [OPINION, with product metrics] Keep one writer: "multi-agent systems work best today when writes stay single-threaded". 2026-04-22 *(opened)* — [Cognition](https://cognition.com/blog/multi-agents-working)
- [GUIDANCE] Allowlists: limit outbound requests to trusted addresses (Meta's travel-assistant example), restrict image rendering to allow-listed domains (CSA), and use allowlist-based rather than blocklist-based URL validation (MCP) *(opened)* — [Meta AI](https://ai.meta.com/blog/practical-ai-agent-security/); [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-indirect-prompt-injection-in-the-wild-2026/); [MCP Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)
- [GUIDANCE] Treat content from other agents as data, not instructions: record where input came from, keep instructions and data in separate structured fields, and stop a session that drifts from the original request *(opened)* — [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-indirect-prompt-injection-in-the-wild-2026/); [Unit 42](https://unit42.paloaltonetworks.com/agent-session-smuggling-in-agent2agent-systems/)
- [GUIDANCE] Filters alone are not enough: deny-listing known attack phrases is easily bypassed (NCSC), and 12 published defences fell to adaptive attacks *(opened)* — [NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection); [arXiv 2510.09023](https://arxiv.org/abs/2510.09023)
- [GUIDANCE] Human approval for sensitive actions, tied to the specific action rather than the whole output, with state saved while waiting *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns); [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- [INCIDENT] Approval must sit outside the assistant: approval prompts were auto-clicked by a browser extension (2026-11-06) and approval-gated tools were triggered from another web page (2026-10-08) *(aggregator, primaries not opened)* — [The Hacker News](https://thehackernews.com/2026/11/malicious-browser-extensions-could-use.html); [GitHub advisory](https://github.com/advisories/GHSA-h4xc-3qfq-jf93)
- [GUIDANCE] Audit logs: log inputs, outputs and tool calls to detect suspicious activity (NCSC); "Lack of Audit and Telemetry" is a named MCP risk (OWASP); "Design audit trails to meet compliance requirements" (Microsoft) *(opened)* — [NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection); [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/); [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [GUIDANCE] Rate and cost limits: "To guard against infinite tool-call loops, set iteration limits"; monitor "token consumption per agent and per orchestration run"; logging and rate limiting limit the damage of excessive agency *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns); [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- [INCIDENT] A leaked hub token is also a bill: the Flowise flaw let unauthenticated callers spend the owner's model quota (2026-11-17) *(aggregator, primary not opened)* — [VulnCheck](https://www.vulncheck.com/advisories/flowise-3.1.3-through-3.1.4-mcp-server-token-disclosure-via-public-chatflow-endpoint)
- [MEASURED] Loops are a leading failure: step repetition (15.7%) and not recognising when to stop (12.4%) are two of the most common multi-agent failure modes. v3 dated 2025-10-26 *(opened)* — [arXiv 2503.13657 v3](https://arxiv.org/html/2503.13657v3)
- [INCIDENT] Keep secrets out of messages and memory: Moltbook's leaked agent-to-agent messages contained third-party API keys in plain text. 2026-02-02 *(opened)* — [Wiz](https://www.wiz.io/blog/exposed-moltbook-database-reveals-millions-of-api-keys)
- [INCIDENT] Basic web-app hygiene matters more than agent logic: Moltbook failed on a database key in client code and missing row-level access rules, and about 35,578 AI-generated apps were found open without sign-in in November 2026 *(opened; second item aggregator)* — [Wiz](https://www.wiz.io/blog/exposed-moltbook-database-reveals-millions-of-api-keys); [The Hacker News](https://thehackernews.com/2026/11/over-35000-grok-built-apps-exposed.html)
- [SPEC] Duplicates and retries: accept a caller-supplied request identifier, return the original result for a repeat, and reject the same identifier with different content; hold tasks under an expiring lease rather than a permanent lock *(opened)* — [AWS Builders' Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/); [AWS SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)
- [GUIDANCE] Memory hygiene: periodically review what each assistant has stored about you and delete entries you do not recognise. 2026-02-10 *(opened)* — [Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2026/02/10/ai-recommendation-poisoning/)
- [GUIDANCE] Rule of Two applied per assistant session: if a session reads untrusted content and holds private data, it should not also be able to send or change things without a person approving. 2025-10-31 *(opened)* — [Meta AI](https://ai.meta.com/blog/practical-ai-agent-security/)

### Inferences
- A one-person version of the list, in order of value for effort: (1) a separate key per assistant and per person, revocable, shown only once; (2) each key limited to named actions, with "read" and "propose" by default and "write" only for the assistant that needs it; (3) every write or outbound action from an assistant lands as a proposal that the owner approves on the hub's own screen; (4) every entry stored with who wrote it, from which source, and when, and passed to other assistants as quoted material with that label; (5) a per-key daily cap on requests and on tasks created, plus a maximum number of steps per task; (6) a request identifier on every submission so repeats do not create duplicates; (7) a log of every request, approval and refusal that the assistants cannot edit.
- "Treat as data" is a labelling and permissions practice, not a filter: the hub cannot make an assistant ignore instructions, so the safe design is that whatever an assistant decides after reading hub content, it can only produce a proposal.
- The assistant holding the most sensitive data should have the narrowest hub permissions. If the corporate assistant participates at all, the safest role is "posts tasks and short status notes, reads nothing written by other assistants".

### Gaps
- No authoritative checklist written for a single person or a very small team was found; the list above is assembled from enterprise-oriented guidance and incident lessons.
- How each consumer assistant authenticates to a custom HTTP API (key or OAuth for a custom GPT, Claude connectors, Copilot Studio, Grok) was outside the pages I could fetch and is not covered here.
- No measured data on how often human approval steps are approved without reading; Meta notes the risk that a user confirms a warning without reading it, but gives no numbers.

## 5. Corporate governance: linking a corporate assistant that holds company data with personal or consumer assistants

### Takeaway
The employer's Copilot runs under contractual, residency and permission guarantees that end at the tenant boundary; a personal hub and consumer assistants are outside it, and moving work content across is the "shadow AI" pattern that regulators and breach studies single out. The defensible pattern is that company content stays in the tenant and only tasks, short status notes or non-sensitive metadata cross, and that any technical connection from the tenant is one the company's administrators have approved.

### Cited Findings

#### What the corporate tenant guarantees, and where it stops

### Inferences
- Typical company rules, as reflected in the regulator checklists and the admin controls above: only approved tools; work accounts, not personal ones; defined categories of data that may never be entered; no new outbound connection from a company agent without administrator approval; incidents reported. The reader should assume their employer has rules of this kind and read them before linking anything.
- Connecting the tenant Copilot to a personal hub means building an agent or connector in the tenant that calls an outside address. Whether that is even possible depends on the tenant's data policies, and doing it would make the hub a recipient of company data under the employer's confidentiality and data-protection obligations. Copying Copilot output by hand into a personal assistant is the same transfer without the technical control.
- Patterns the sources support as safe: (a) company content stays in the tenant; what crosses is a task title, a deadline, a status or a pointer such as a document name, never the content; (b) the personal hub treats the corporate assistant as write-only at most ("post a reminder"), so nothing flows back into the tenant from other assistants; (c) if richer integration is wanted, it is requested through IT as an approved agent or connector, and the other assistants are used under business plans whose terms exclude training and offer audit; (d) personal and work memory are kept apart in each assistant.
- Even task titles can be confidential (a client name, a deal). "Metadata only" needs a simple personal rule about what a title may contain.
- Data residency is a second, separate constraint: a hub hosted in another country and consumer assistants processing in the United States may conflict with commitments the employer has made, independently of training policies.

### Gaps
- xAI's consumer and business data terms for Grok could not be opened (the legal pages returned an access error) and searches were no longer available, so Grok's training, retention and business-plan terms are unverified here.
- The Hong Kong, Hamburg, Turkish, Singaporean and Australian regulator documents were not opened in full; the points above come from search summaries and one law-firm summary.
- Microsoft Purview controls for detecting or blocking pasting of sensitive content into outside AI sites were not fetched.
- The reader's own employer policy, contract and jurisdiction are unknown and decisive; none of this was researched, by instruction.
- I found no published example of an employer explicitly approving a personal coordination hub connected to a tenant assistant, and no regulator text that addresses agent-to-agent links specifically.
- OpenAI's enterprise privacy page does not state data-residency regions.

## 6. Observability: what to log and show to supervise several agents, and which standards and tools exist

### Takeaway
There is one emerging standard, OpenTelemetry's generative-AI conventions with spans for agent runs and tool calls, but as of late 2026 it is still marked in development and consumer assistants do not report into a user's own monitoring. For a personal hub the practical answer is that the hub itself is the record: it should log every task, hand-off, approval, refusal and cost by agent key, and the orchestration screen is a view of that log.

### Cited Findings
- [SPEC] OpenTelemetry's generative-AI conventions have moved out of the main specification: the documentation page now says "GenAI semantic conventions have moved to the OpenTelemetry GenAI semantic conventions repository". Fetched 2026-11-23 *(opened)* — [OpenTelemetry docs](https://opentelemetry.io/docs/specs/semconv/gen-ai/)
- [SPEC] The new repository covers "spans, metrics, and events for GenAI clients", MCP conventions and provider-specific conventions; it shows no tagged release and its schema-URL section reads "TODO". Fetched 2026-11-23 *(opened)* — [open-telemetry/semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai)
- [SPEC, secondary] Third-party status reports from July–August 2026 say all 63 `gen_ai` attributes are still at "Development" stability, that version 1.42.0 of the main conventions (2026-06-12) deprecated the namespace there in favour of the new repository (created 2026-05-05), and that the span model is: `chat` for a model call, `invoke_agent` for an agent run, `execute_tool` for a tool call, `create_agent` when an agent is built *(secondary, from search summary; status after August 2026 not confirmed)* — [John Hodge, July 2026](https://john-hodge.com/blog/opentelemetry-genai-semantic-conventions/); [Particula](https://particula.tech/blog/opentelemetry-genai-semantic-conventions-stable)
- [GUIDANCE] OpenTelemetry's 2025 article on agent observability: an initial agent application convention exists (based on Google's agent white paper) and a common convention for agent frameworks was still under discussion; frameworks either ship built-in telemetry or rely on separate instrumentation libraries; systems should emit traces, metrics and logs, which also feed evaluation. Named frameworks: CrewAI, AutoGen, Semantic Kernel, LangGraph, PydanticAI, IBM Bee AI. Published 2025 (exact day not shown on the fetched page) *(opened)* — [OpenTelemetry blog, AI Agent Observability](https://opentelemetry.io/blog/2025/ai-agent-observability/)
- [GUIDANCE] Microsoft: "Instrument all agent operations and handoffs"; "Track performance and resource usage metrics for each agent"; "monitor token consumption per agent and per orchestration run"; test with scoring rubrics or model-as-judge because outputs are not deterministic. Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [GUIDANCE] Anthropic: full production tracing was needed to diagnose failures, and the team monitors "agent decision patterns and interaction structures" without reading the contents of individual conversations, to preserve privacy. 2025-06-13 *(opened)* — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- [GUIDANCE] What to show the person supervising: tool invocations, live execution logs and indicators that a remote agent sent instructions, so that suspicious activity is visible. 2025-10-31 *(opened)* — [Unit 42](https://unit42.paloaltonetworks.com/agent-session-smuggling-in-agent2agent-systems/)
- [SPEC] Log permission changes with identifiers that tie events together: "Log elevation events (scope requested, granted subset) with correlation IDs" *(opened)* — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)
- [SPEC] A2A gives ready-made correlation keys: a server-generated task ID per task and a contextId that groups related tasks and messages *(opened)* — [A2A Protocol Specification](https://a2a-protocol.org/latest/specification/)
- [GUIDANCE] Security logging: log inputs, outputs and tool calls (NCSC); keep tool-call audit trails (CSA); missing telemetry is itself a listed risk, "MCP08:2025 – Lack of Audit and Telemetry" (OWASP) *(opened)* — [NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection); [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-indirect-prompt-injection-in-the-wild-2026/); [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/)
- [GUIDANCE] Cost supervision in one vendor's tooling: Claude Code attributes usage to subagents, plugins and individual MCP servers, supports spend limits per organisation, group or person, and "OpenTelemetry export works on every setup and is the only option that streams per-user token and cost metrics into your own observability stack in near real time"; a gateway that tracks spend per key is another option. Living documentation *(opened)* — [Claude Code docs, Manage costs effectively](https://code.claude.com/docs/en/costs)
- [GUIDANCE] What the vendors already record for administrators: Microsoft stores Copilot prompts and responses, searchable and subject to retention policies in Purview (dated 2026-07-09); OpenAI gives Enterprise administrators an audit log of conversations and GPTs through its Enterprise Compliance API (page updated 2026-01-08) *(opened)* — [Microsoft Learn](https://learn.microsoft.com/en-us/copilot/microsoft-365/microsoft-365-copilot-privacy); [OpenAI, Enterprise privacy](https://openai.com/enterprise-privacy/)
- [GUIDANCE] IBM's 2026 report recommends human attribution and auditability for agent identities. 2026 *(opened)* — [IBM](https://www.ibm.com/reports/data-breach)
- [GUIDANCE] The magentic pattern's ledger doubles as the supervision record: plan, task statuses and "a complete audit trail of the evolving plan and the implementation steps". Dated 2026-02-12 *(opened)* — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- [INCIDENT] Third-party gateways and agent packages are themselves supply-chain targets: malicious releases of a widely used LLM gateway (2026-10-21) and of an agent framework package (2026-11-17) stole credentials at start-up *(aggregator, primaries not opened)* — [Wiz, LiteLLM](https://www.wiz.io/blog/litellm-compromised-steals-credentials); [Wiz, agent-framework](https://www.wiz.io/blog/malicious-version-of-microsofts-agent-framework-published-to-pypi)

### Inferences
- A minimal record per event for the hub, drawn from the items above: time; which key (agent and person); action; task ID and thread ID; state before and after; who or what approved it; source of the content (typed by the owner, another agent, an external document); size or cost if known; outcome or error.
- A minimal orchestration screen: tasks grouped by state using the A2A names (submitted, working, input required, completed, failed, cancelled, rejected); current owner and time left on its lease; the chain of hand-offs for each task; a queue of pending approvals; a daily count of requests and cost per agent with a visible cap; a list of refusals and errors; a filter for "content that came from another agent or an outside source".
- Because consumer assistants do not send traces to a user's collector, cross-vendor tracing in the OpenTelemetry sense is not available to an individual today; adopting the OpenTelemetry names for agent, tool call and token counts in the hub's own log would keep the door open without depending on a standard that is still changing. This is my reading; I found no source that addresses the individual-user case.
- Logging raises its own governance question: a hub log that contains corporate content is a copy of corporate data. Logging identifiers, states and sizes rather than full text is consistent with Anthropic's practice and with Microsoft's advice to keep persisted state minimal.

### Gaps
- The stability status of the OpenTelemetry generative-AI conventions after August 2026 could not be confirmed from a primary source; the repository shows no release.
- A vendor-neutral comparison of observability products for agents (for example LangSmith, Langfuse, Arize Phoenix, Datadog, MLflow) was not retrieved; they are not assessed here.
- NIST AI 800-4 on post-deployment monitoring was not opened.
- I found no standard or documented practice for propagating one trace across assistants from different vendors when the "orchestrator" is a person's own small web app.
